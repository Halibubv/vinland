# Путеводитель по коду

Короткое объяснение, как устроено приложение и где что искать. Удобно
перечитать перед защитой.

## Три части

1. **Интерфейс** (`src/`) — React. Рисует экраны и отправляет запросы на сервер.
   После `pnpm run build` превращается в обычные HTML, JS и CSS в `public/ui`.
2. **Сервер** (`public/index.php` и `backend/`) — PHP без фреймворка.
   Принимает запросы `/api/...`, проверяет данные, работает с базой и отвечает JSON.
3. **База** (`database/`) — PostgreSQL. Таблицы описаны в SQL-файлах `001`–`004`,
   их по порядку выполняет `migrate.php`.

## Путь одного действия: «Сохранить приём пищи»

1. Пользователь нажимает «Сохранить в дневник» на экране
   `src/pages/MealEditor.jsx`. Срабатывает функция `save`: она проверяет, что
   продукты есть и граммы больше нуля, и собирает объект с датой, типом и продуктами.
2. `save` вызывает `api('/meals', { method: 'POST', body })` из `src/lib/api.js`.
   Эта функция делает `fetch` на `/api/meals`, добавляет заголовок с CSRF-токеном
   и превращает ответ сервера в объект или в понятную ошибку.
3. Запрос приходит в `public/index.php`. Это таблица маршрутов: метод + адрес →
   функция. Для `POST /api/meals` вызываются:
   - `require_user()` (`backend/database.php`) — кто вошёл; если никто, ответ 401;
   - `read_json()` (`backend/http.php`) — читает тело запроса;
   - `meal_input()` (`backend/meals.php`) — проверяет поля через функции из
     `backend/validation.php`; при ошибке ответ 422 с текстом для пользователя;
   - `write_meal()` — в одной транзакции сохраняет приём пищи и продукты.
     Вместе с продуктом записываются его название и КБЖУ на этот день (снимок),
     чтобы правка справочника не меняла старые записи.
4. `respond()` отправляет JSON с сохранённым приёмом пищи. Интерфейс получает
   ответ и переходит обратно в дневник (`navigate(...)` из `src/lib/router.js`).

Остальные действия (тренировки, профиль, справочники админа) устроены так же:
экран → `api()` → маршрут в `index.php` → функция в `backend/` → база → JSON.

## Где что искать

| Что нужно найти | Где |
| --- | --- |
| Какой экран открывается по адресу | `src/App.jsx`, функция `SectionPage` |
| Шапка, меню, подвал | `src/components/Layout.jsx` |
| Общие кусочки: поле формы, полоса прогресса, пустое состояние | `src/components/ui.jsx` |
| Окна подтверждения и выбора из справочника | `src/components/Dialogs.jsx` |

| Переходы между страницами без перезагрузки | `src/lib/router.js` |
| Стили экрана | `.css` рядом с экраном в `src/pages/` |

## Что из React здесь используется

- **Компонент** — функция, которая возвращает разметку (JSX). Каждый экран в
  `src/pages/` — компонент.
- **`useState`** — данные экрана, которые меняются: введённый текст, загруженный
  список, текст ошибки. После `setЧто-то(...)` React перерисовывает экран.
- **`useEffect`** — код, который выполняется после показа экрана. Здесь он почти
  всегда загружает данные с сервера.
- **props** — параметры, которые компонент получает от родителя, например
  `<MealEditor id={mealId} />`.

Больше ничего (Redux, React Router, TypeScript) в проекте нет специально,
чтобы код можно было прочитать без лишних знаний.

## Безопасность в двух словах

- Пароли хранятся только в виде хеша (`password_hash`).
- Каждый запрос, который что-то меняет, должен прислать CSRF-токен.
- Сервер всегда проверяет, что тренировка или приём пищи принадлежит
  пользователю, который их запрашивает.
- Данные от пользователя попадают в SQL только как параметры подготовленного
  запроса (`query($sql, $parameters)`), поэтому SQL-инъекция через них не пройдёт.
